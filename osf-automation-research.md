# OSF Automation Options for Plimsoll Gate 0.5 Pre-Registration

## TL;DR

OSF exposes a fully documented JSON:API v2 (`api.osf.io/v2/`) that supports the entire pre-registration lifecycle — create draft, set schema, fill schema responses, attach a project, and submit — using a Personal Access Token. There is **no official COS MCP server**, but three community OSF MCP servers exist; none of them currently implement registration *creation* (they cover search/projects/files only). Recommended path: skip the MCP servers, write a ~50-line Python script against the documented draft-registration endpoints, and use `osfclient` only if file uploads are needed.

## 1. Official OSF MCP server

**Not found.** A scan of the Center for Open Science GitHub org (96 public repos) returned zero matches for "mcp" in name or description. Most-recently-updated COS repos are infrastructure (`osf.io`, `angular-osf`, `helm-charts`, `ember-osf-web`, `osf-pigeon`) — none mention Model Context Protocol.

- COS GitHub org: https://github.com/CenterForOpenScience
- No MCP-related repos as of 2026-04-26

## 3. OSF REST API capabilities

### Authentication

OSF API v2 uses **HTTP Bearer with a Personal Access Token (PAT)**. Tokens are issued at https://osf.io/settings/tokens with selectable scopes (`osf.full_write`, `osf.users.profile_read`, etc.). API description (swagger.json `info.description`) explicitly says "OAuth-based authentication and authorization". OAuth2 client app flow exists but PAT is the practical option for scripts.

Header: `Authorization: Bearer <token>`

- Docs: https://developer.osf.io/
- Token UI: https://osf.io/settings/tokens
- Getting-started guide: https://help.osf.io/article/377-osf-api-getting-started

### Registration creation

**Yes, fully supported.** The endpoints relevant to creating a pre-registration:

| Endpoint | Method | Purpose |
|---|---|---|
| `/v2/schemas/registrations/` | GET | List available registration schemas (templates). Returns `id`, `name`, `schema_version`, `active`, and the full block-based form schema. |
| `/v2/nodes/{node_id}/draft_registrations/` | POST | Create a draft registration *attached to an existing project*. Required: `schema_id` (relationship). |
| `/v2/draft_registrations/` | POST | Create a draft registration **not yet linked to a project** (link later via `branched_from`). |
| `/v2/draft_registrations/{draft_id}/` | PATCH | Update the draft's metadata and `registration_responses` (the actual answers to the schema questions). |
| `/v2/draft_registrations/{draft_id}/contributors/` | POST | Add co-authors. |
| `/v2/registrations/` | POST | **Finalize / register.** Submits the draft, creating the immutable Registration. Embargo dates are set here. (Inferred from the data model — finalization is "register the draft" with optional embargo, controlled by a `submit` registration_action trigger.) |
| `/v2/registrations/{registration_id}/` | PATCH | Limited: only flip `public` from private→public. |

The `registration_action.trigger` enum includes `submit`, `accept`, `reject`, `edit_comment` — this confirms the moderated-provider workflow uses an explicit `submit` action that the API exposes.

JSON:API format (resource/relationships/attributes envelope). Content type is `application/vnd.api+json`.

Workflow (canonical Plimsoll Gate 0.5 path, project-attached):

1. `POST /v2/nodes/` → create the OSF project.
2. `POST /v2/nodes/{node_id}/draft_registrations/` with `relationships.registration_schema.data = {type: "registration_schemas", id: "<schema_id>"}`.
3. `PATCH /v2/draft_registrations/{draft_id}/` with `attributes.registration_responses = {q1: "...", q2: "...", ...}` keyed by the block IDs from the schema.
4. (Optional) Upload supplementary files via WaterButler (see below).
5. `POST /v2/registrations/` with `relationships.draft_registration.data = {type: "draft_registrations", id: "<draft_id>"}` plus `attributes.embargo_end_date` (optional). This is the irreversible step.

### File upload

OSF uses a separate file service called **WaterButler** (host: `files.osf.io`). Files are uploaded with `PUT https://files.osf.io/v1/resources/{node_id}/providers/osfstorage/?name=<filename>` carrying the binary body and the same `Authorization: Bearer` header. Python wrappers (`osfclient`, `osfr`) are essentially WaterButler clients.

- Individual file size limit: **5 GB**.
- Public project total cap: 50 GB. Private project total cap: 5 GB.
- Source: https://help.osf.io/article/377-osf-api-getting-started (storage caps section).

### Rate limits

**Not publicly documented in numeric terms.** The OSF Help center and developer docs describe authentication and best practices but do not publish a per-second/per-day rate limit. Empirically the API throttles via `429 Too Many Requests` if abused, and unauthenticated traffic is throttled more aggressively than authenticated. Plan to back off on 429s. (If you need a hard number, COS support is the canonical source.)

## 4. Pre-registration specifics

### Supported templates

Live query of `https://api.osf.io/v2/schemas/registrations/?page[size]=50` returned **43 schemas, 41 active**. The general-purpose templates relevant to Plimsoll:

| Schema name | ID | Version |
|---|---|---|
| OSF Preregistration | `697b72f611a8e98484c6139b` | 4 |
| Preregistration Template from AsPredicted.org | `64bab305769023000d0acdc0` | 4 |
| Secondary Data Preregistration | `64775783798e08000a70407e` | 3 |
| Open-Ended Registration | `5df83f7dd28338001ac0ab0d` | 3 |
| Registered Report Protocol Preregistration | `5e795fc0d2833800195735cf` | 4 |
| OSF-Standard Pre-Data Collection Registration | `564d31db8c5e4a7c9694b2c0` | 2 |
| Qualitative Preregistration | `5fa0ac510a7f38001c8ae854` | 1 |
| Replication Recipe (Brandt et al., 2014): Pre-Registration | `64b14a08d639e5000d2013a5` | 1 |

For a Plimsoll capability-margin study, **OSF Preregistration** (the modern OSF default) or **AsPredicted** are the obvious candidates; pick by feature alignment with the existing `pre-registration.md` draft.

The `Prereg Challenge` schema (`565fb3678c5e4a66b5582f67`) is `active: false` — do not use.

### Form field addressability

**Yes — fully addressable via the API.** Each schema returns a `blocks` array describing every question (block_type, display_text, help_text, required). When you `PATCH` a draft registration, you set `attributes.registration_responses` as a flat object keyed by the block IDs from that schema. Example block types observed: `page-heading`, `question-label`, `long-text-input`, `single-select-input`, `select-input-option`. So the registration form fields are not UI-only; you can populate every answer by API.

This means the Plimsoll `pre-registration.md` content can be rendered into the OSF draft without manual web-UI typing.

### Existing automation precedents

- `osf-pigeon` (CenterForOpenScience): scripts that use the v2 API to **archive** registration data (read direction). https://github.com/CenterForOpenScience/osf-pigeon — confirms the v2 API is production-grade enough that COS itself uses it for downstream automation.
- `ropensci/osfr`: end-to-end project/file management in R; does **not** include registration functions (verified — no `osf_register*` in R/ source).
- No prominent open-source examples specifically of "fill a draft preregistration via the API" were located in this scan, but the endpoint contract is clear and the API is JSON:API standard.

## 6. OSF Preprints API

Preprint upload **is** automatable. Endpoints:

- `POST /v2/preprints/` — create a preprint
- `POST /v2/preprints/{id}/versions/` — new version
- `PATCH /v2/preprints/{id}/` — edit metadata
- `POST /v2/preprints/{id}/contributors/` — add co-authors
- `POST /v2/preprints/{id}/requests/` + `POST /v2/actions/requests/preprints/` — moderation submission flow
- File body upload via WaterButler (`files.osf.io`)

So if you want to put the eventual Plimsoll Gate 0.5 PDF on OSF Preprints (or e.g. PsyArXiv, which uses the same OSF backend), the same script can do it with a different schema. Out of scope for the immediate Gate 0.5 pre-reg step but a natural extension.

## Recommendation for Plimsoll Gate 0.5

**Option (b): write a small custom Python script directly against the OSF v2 REST API.** Concretely:

1. Generate a PAT at https://osf.io/settings/tokens with `osf.full_write` scope.
2. Write `~50 lines` of Python (`requests` only, no SDK) that:
   - Creates the OSF project (`POST /v2/nodes/`).
   - Creates the draft registration with `schema_id = 697b72f611a8e98484c6139b` (OSF Preregistration v4) or AsPredicted.
   - PATCHes `registration_responses` with the field-keyed answers extracted from `pre-registration.md`.
   - (Optional) Uploads supplementary files (the inventory CSVs, simulation script) via WaterButler.
   - POSTs to `/v2/registrations/` to finalize, optionally with `embargo_end_date`.
3. Commit the script to the gate-0.5 directory so the registration is reproducible (and re-runnable for the planned re-registration / Change 2 step).

**Why not the other paths:**

- **(a) Web UI:** Works, but you lose reproducibility, the responses aren't version-controlled outside the markdown source, and you've already noted Change 2 (re-registration) on the docket — manual UI re-entry is the wrong tool for a process that will repeat.
- **(c) Existing client (`osfclient` / `osfr`):** Neither supports registration creation. Using one for files only adds a dependency for a 4-line WaterButler PUT.
- **(d) Build / install MCP server:** Costs more than the script saves. None of the existing servers cover registration creation, so you'd be writing the same 50 lines wrapped in MCP boilerplate. Only worth it if you expect Claude to drive *many* registrations interactively, which isn't Plimsoll's pattern.

**Side benefit of (b):** The same script template can be reused for the Plimsoll preprint upload to OSF Preprints / PsyArXiv when Gate 1 ships, and (if the methodology generalizes) for future registrations across the Research vault.
